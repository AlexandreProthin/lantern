# Ground rules

The rules of [v0.1.0](/plans/v0-1-0.md) still hold: every task cites its spec ids; a spec that
turns out wrong is changed first, then the code; the core knows no room. The review question
becomes concrete: *does this file name `learn` or `choose`?* Only `app/src/rooms/<id>/`, the room
list (RS-4) and tests may.

**Two releases** (q-r5-release): Part A ships alone and must leave Learn exactly as it is; Part B
lands on top of it. Version numbers: Part A is **v0.2.0** (the format change makes it a minor
version); Part B ships as the next version once accepted (v0.2.x or v0.3.0, the user's call at
release time).

Checks run for every slice: `npm run check` 0/0, the TypeScript unit tests, the Rust tests, and the
Playwright suite on a private port. Prompt changes also need the three-run eval gate (PQ-33).

# Part A: room-generic frame, lantern/2, Learn unchanged

## A1. Finish the format spec

- Write the exact `lantern/2` field list in [domain-model](/specs/domain-model.md) DM-4 and its
  example: the core fields, what moves into node and visit `data` for Learn (`understoodBy`, `tone`,
  `direction`?), roles `user`/`model`, `task` as a string, the optional web-call count in a log record.
- Write the `lantern/1 → lantern/2` conversion in [subject-storage](/specs/subject-storage.md):

- Decide where room data is validated: the Rust side today validates the whole subject on every

- **Exit:** the user agrees the field list (a short workshop round or chat confirmation).
- **Written 2026-10-13**, awaiting the user: [domain-model](/specs/domain-model.md) DM-60 to DM-68
  and its `lantern/2` example, [subject-storage](/specs/subject-storage.md) ST-7 (per-room summary),
